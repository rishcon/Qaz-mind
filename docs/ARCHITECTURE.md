# Архитектура QazMind

## 1. Состав

```
qazmind/
  apps/
    web/          QazMind Web: лендинг, аккаунт ученика, уроки, практика, школы (демо)   :5173
    admin/        QazMind Admin: панель платформы (демо-данные, без входа)              :5174
    api/          FastAPI backend, PostgreSQL, миграции Alembic, CLI контента          :8000
  packages/
    contracts/    общий HTTP-клиент, типы ошибок и страниц, пути админского API
  docs/           архитектура, интеграция, контракты, примеры развёртывания
  scripts/        одноразовые утилиты (экспорт прототипных уроков)
```

Приложения самостоятельные: у каждого своя точка входа, `vite.config.ts`, `tsconfig.json`, `package.json` и независимая сборка. Общие части вынесены только если их используют оба приложения: HTTP-транспорт и типы (`packages/contracts`).

Инструменты: npm workspaces (без Turborepo, Nx и прочих систем сборки) и `concurrently` для запуска двух фронтендов одной командой. Скрипты кроссплатформенные, работают в Windows без bash.

## 2. Порты и адреса

| Сервис | Локально | Production (план) |
|---|---|---|
| QazMind Web | http://localhost:5173 | https://qazmind.asia |
| QazMind Admin | http://localhost:5174 | https://admin.qazmind.asia |
| API | http://localhost:8000 (`/api/v1`) | https://api.qazmind.asia |
| PostgreSQL (Docker) | localhost:55432 | внутренний адрес |
| Mailpit (локальная почта) | SMTP 1025, веб-интерфейс http://localhost:8025 | — |

Фронтенды слушают только `127.0.0.1` (как требует задача). Для доступа с другого устройства нужно явно передать `--host` и открыть порт в сети.

Каждый фронтенд проксирует `/api` на API. Браузер видит один origin на приложение, поэтому cookie сессии работает без CORS-обходов. Cookie host-only: адреса `localhost:5173` и `localhost:5174` делят cookie одного хоста, но запросы каждого приложения идут через его собственный прокси.

## 3. Кому что принадлежит

| Данные | Владелец | Кто читает | Кто меняет |
|---|---|---|---|
| Пользователи, пароли, сессии, роли | API (PostgreSQL) | Web (свой профиль), Admin (по роли) | API |
| Профили обучения | API | Web | Web через API |
| Предметы, темы, уроки, версии | API | Web (опубликованные), Admin | Admin через API (план), CLI (сейчас) |
| Вопросы и банк | API (план) | Admin, Web через учебный API | Admin через API (план) |
| Прогресс уроков и попытки | API | Web, Admin (агрегаты) | Web через API |
| Школы, классы, задания, результаты | API (план, этапы 6–8) | Web, Admin | Web (учитель/школа), Admin |
| Журнал административных действий | API (план) | Admin | Только сервер |

Правило: ни одно приложение не хранит истину о пользователях или учебном контенте в браузере. `localStorage` допустим только для UI-состояния (открытые вкладки, свёрнутые панели, черновик формы).

## 4. Аутентификация и доступ

Сейчас:
- Один аккаунт для всей платформы: регистрация только в QazMind Web.
- Сессия в HttpOnly cookie, CSRF double-submit, проверка `Origin` для изменяющих запросов.
- Администраторского входа нет. QazMind Admin работает только в демо-режиме (см. §5), а в production-сборке без флага показывает экран «доступ только для сотрудников».
- QazMind Web показывает ссылку на админку только в демо-режиме.

План (не реализовано):
- Роли платформы хранятся в БД (`OWNER`, `PLATFORM_ADMIN`, `CONTENT_EDITOR`, `CONTENT_REVIEWER`, `SUPPORT`), назначаются только доверенной операцией, не формой регистрации.
- Вход администраторов с обязательной MFA. Каждое административное действие пишется в журнал.
- Проверка прав — только на сервере при каждом запросе. Фронтенд может скрывать пункты меню, но этого недостаточно.

## 5. Демо-режимы

Оба приложения содержат части на вымышленных данных. Каждая такая часть помечена на экране.

| Режим | Где включается | Что видно |
|---|---|---|
| Web `VITE_DEMO_MODE=true` | только локально | прототип школ, учителя, заявка школы, ссылка на админку |
| Admin `VITE_ADMIN_DEMO_MODE` | в dev включён по умолчанию; в production выключен | вся панель, плашка «ДЕМО-РЕЖИМ» внизу экрана, переключатель ролей |

Переключение ролей в админке работает только в памяти браузера и не меняет права на сервере. В production без флага его не видно, потому что панель закрыта экраном доступа.

## 6. Что работает и что нет

Работает сквозным образом (проверено на запущенном стеке):
- регистрация, письмо в Mailpit, подтверждение, вход, выход;
- онбординг и профиль на сервере;
- учебный контент: опубликованный урок виден ученику, прогресс сохраняется, завершение фиксируется;
- оба фронтенда запускаются одной командой на своих портах, прокси `/api` работает из обоих.

Не работает или работает на моках: см. `docs/INTEGRATION.md`, раздел «Технический долг».

## 7. Решения

- **npm workspaces, а не монорепо-инструменты.** Два фронтенда и общий пакет — достаточно простой схемы. Turborepo не нужен, пока нет долгих сборок.
- **Один backend для обоих фронтендов.** Отдельный backend для админки отвергнут: две базы пользователей и два источника вопросов привели бы к расхождениям.
- **Общий пакет только для транспорта и контрактов.** Экраны и сервисы каждого приложения остаются в нём; объединять `App.tsx` не стали.
- **Порты задаются строго (`strictPort`).** Если порт занят, dev-сервер падает с ошибкой, а не переходит на другой порт и не путает адреса.
- **Mailpit для локальной почты.** Письма никуда не уходят, ссылки видны в интерфейсе.
