# Доступ к QazMind Admin: роли, вход, владелец и аудит

Статус: **проект**. Вход сотрудников, административный API и выдача ролей не реализованы. QazMind Admin сейчас не показывает данных и не выполняет записей: каждое изменение отказывается с понятным сообщением (см. [INTEGRATION.md](INTEGRATION.md)). Этот документ фиксирует модель, по которой всё будет построено.

Пункты, помеченные **(предложение)**, не согласованы с владельцем платформы. Список открытых решений — в разделе 10.

## 1. Принципы

- **Права проверяет сервер на каждом запросе.** Скрытый пункт меню или проверка в браузере — только удобство интерфейса. Защитой они не являются.
- **Роли выдаёт только владелец платформы.** Никто не назначает роль себе. Самостоятельной регистрации администраторов нет, публичной кнопки «Стать администратором» тоже нет.
- **Признак доступа не хранится в браузере.** Роли читаются с сервера при входе и на каждом запросе. `localStorage` и `sessionStorage` доказательством прав не служат.
- **Вход сотрудника защищён двухфакторной аутентификацией (MFA).** Без MFA сотрудник не получает доступа ни к одному разделу, кроме экрана настройки MFA.
- **Разделение обязанностей.** Тот, кто создал материал, не утверждает и не публикует его.
- **Каждое административное действие пишется в журнал аудита на сервере.** Записи нельзя изменить или удалить ни через интерфейс, ни через API.
- **Минимум прав.** Роль даёт только то, что нужно её задачам.

## 2. Владелец платформы

- Первого владельца создаёт **серверная команда**, а не интерфейс. Команда запускается на сервере с доступом к базе и работает один раз:
  `python -m app.admin.cli bootstrap-owner --email <адрес>` **(предложение)**.
- Если владелец уже есть, команда отказывает. Повторный запуск без процедуры восстановления невозможен.
- Команда создаёт учётную запись владельца в состоянии «приглашён» и отправляет письмо со ссылкой. Владелец задаёт пароль и настраивает MFA.
- Роль `OWNER` может назначить только существующий владелец. Последнего владельца отключить нельзя.
- Восстановление доступа, если владелец потерял MFA, — открытое решение (раздел 10).

## 3. Жизненный цикл сотрудника

1. **Приглашение.** Владелец указывает email и набор ролей. Сервер создаёт приглашение с одноразовой ссылкой. Срок ссылки — 72 часа **(предложение)**.
2. **Принятие.** Сотрудник открывает ссылку, задаёт пароль и настраивает MFA. Пароль сотрудника строже пароля ученика: не менее 12 символов **(предложение)**.
3. **Работа.** Сотрудник видит только разделы своих ролей. Владелец видит статус каждого сотрудника: «приглашён», «активен», «отключён», дату последнего входа.
4. **Смена ролей.** Только владелец. Новые права действуют на следующем запросе сотрудника: сессии не продлеваются со старыми правами.
5. **Отключение.** Все сессии сотрудника завершаются. Учётная запись не удаляется, история его действий остаётся в журнале.

## 4. Сессии и повторная проверка

- Сессия сотрудника короче сессии ученика: 8 часов абсолютного срока и 30 минут без активности **(предложение)**.
- Сессия отдельная: собственный cookie, не тот, что у учеников.
- Критичные действия требуют повторного ввода MFA: назначение ролей, публикация экзамена, отключение сотрудника, отзыв сессий.
- Выход из системы завершает сессию на сервере, а не только в браузере.

## 5. Роли

Роли канонические и совпадают в QazMind Admin (`RoleType`) и в `packages/contracts` (`PLATFORM_ROLES`). Одна учётная запись может иметь несколько ролей.

| Роль | Кто это | Зачем нужна |
|---|---|---|
| `OWNER` | Владелец платформы | Всё, включая приглашение сотрудников, назначение ролей и настройки. Единственный, кто выдаёт роли. |
| `PLATFORM_ADMIN` | Администратор платформы | Ежедневное управление: пользователи, школы, поддержка, жалобы, мониторинг, журнал аудита. Не выдаёт роли и не меняет настройки. |
| `CONTENT_MANAGER` | Контент-менеджер | Создаёт предметы, темы, вопросы, уроки и конструирует экзамены. Не рецензирует и не публикует. |
| `CONTENT_REVIEWER` | Методист-рецензент | Рецензирует задания, утверждает и публикует. Не создаёт задания сам. |
| `SUPPORT_AGENT` | Поддержка | Обращения пользователей и школ, разбор жалоб, просмотр пользователей. |
| `FINANCE_MANAGER` | Лицензии и финансы | Квоты мест и учёт школьных лицензий. Платежи не подключены: ценовая модель не утверждена. |
| `ANALYST` | Аналитик | Только чтение аналитики, мониторинга и школ. Телефоны пользователей скрыты. |

## 7. Правила разделения обязанностей (предложение, сервер ещё не реализован)

Проверяет сервер, по учётной записи, а не по ролям в интерфейсе:

- Автор материала не рецензирует, не утверждает и не публикует его. Сравниваются учётная запись автора и текущего сотрудника.
- Задание, которое вернули на доработку, снова утверждает другой сотрудник, с правом `content.review`.
- Решение по жалобе записывается с резолюцией. Закрыть жалобу без резолюции нельзя.
- Владелец не может отключить себя, если он последний владелец.

## 8. Журнал аудита

- **Что пишется:** вход и неудачные входы, события MFA, приглашения, принятие приглашений, смена ролей, отключения, отзыв сессий, одобрение и отклонение школ, изменение квот, публикация и отзыв заданий, решения по жалобам, изменение настроек, выгрузка данных.
- **Что в записи:** кто (учётная запись и роли на момент действия), что сделано, над каким объектом (тип и идентификатор), когда (UTC), результат, идентификатор запроса. Для изменений — значения до и после.
- **Доступ:** чтение по праву `audit.read`. Изменение и удаление записей невозможны.
- Интерфейс не показывает «зафиксировано в журнале», пока журнал не подключён.

## 9. Планируемый API

Пути описаны в `packages/contracts/src/admin.ts`. Всё работает в том же приложении FastAPI, с теми же проверками `Origin` и CSRF, что и API учеников, но с отдельным cookie сессии сотрудника.

- Вход: `POST /admin/auth/login`, `POST /admin/auth/mfa`, `POST /admin/auth/logout`, `GET /admin/auth/me`.
- Сотрудники (только владелец): `GET /admin/staff`, `POST /admin/staff/invitations`, `PATCH /admin/staff/{id}/roles`, `POST /admin/staff/{id}/disable`, `POST /admin/staff/{id}/sessions/revoke`.
- Журнал: `GET /admin/audit`.

Ответ `GET /admin/auth/me` содержит роли и права, которые сервер проверил. Интерфейс по нему решает, что показать. Это удобство, а не защита.

## 10. Открытые решения

Нужен ответ владельца платформы, прежде чем это будет реализовано:

1. **Способ MFA.** Приложение-генератор кода (TOTP) или код на почту. Рекомендация: TOTP, почта — только запасной способ.
2. **Сроки.** Сессия сотрудника 8 часов и 30 минут без активности, приглашение 72 часа, пароль от 12 символов — всё это предложения.
3. **Приглашения.** Может ли `PLATFORM_ADMIN` приглашать сотрудников. Предложение: нет, только `OWNER`.
4. **Восстановление владельца.** Что делать, если владелец потерял MFA и пароль. Варианты: вторая серверная процедура с записью в журнал, или два владельца.
5. **Финансовая роль.** Нужна ли `FINANCE_MANAGER` до утверждения ценовой модели (открытое решение в ТЗ, раздел 22.10).
6. **Школьные администраторы.** Это аккаунты школ, а не сотрудники платформы. Их доступ описывается отдельно, в этапе школьного кабинета.

## 11. Что уже сделано

- QazMind Admin не показывает данных и не выполняет записей. Приглашение сотрудника отключено до появления сервера и входа владельца.
- Список ролей и пути API в `packages/contracts` совпадают с этим документом.
- Экран «Администраторы и роли» показывает матрицу из раздела 6. Она описывает правила, а не выданные права.
- Сам вход, API и выдача ролей не реализованы.
