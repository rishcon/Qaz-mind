# QazMind — техническое задание на развитие платформы

**Версия:** 1.0  
**Дата:** 27.10.2026  
**Статус:** проект ТЗ для реализации через Claude Code  
**Проект:** QazMind / QazMind Personal / QazMind Schools  
**База:** архив `qazmind-—-платформа-осознанной-подготовки-к-ент(1).zip`  
**Основное правило:** сохраняем существующий React-фронтенд и бренд; реализуем настоящий backend, PostgreSQL, безопасность, образовательный движок и школьные процессы.

> **Важно.** Документ определяет целевую архитектуру и критерии приёмки. Он не утверждает, что перечисленные серверные функции уже существуют. Текущие данные и операции на стороне браузера являются прототипом. Продакшен-доступ к реальным ученикам и школам запрещён до выполнения раздела «Безопасность и готовность к запуску».

## 1. Цель и границы проекта

### 1.1. Цель

Преобразовать QazMind из демонстрационного клиентского приложения в полнофункциональный многопользовательский EdTech-сервис для подготовки к ЕНТ/ҰБТ на русском и казахском языках.

**Три основные продуктовые линии:**
1. **Personal:** регистрация ученика, онбординг, уроки, практика, повторение, пробные экзамены, личный прогресс.
2. **Schools:** заявки на подключение организаций, классы, сотрудники, приглашения, лицензии, школьные задания и агрегированные результаты.
3. **Teacher:** назначение доступного учебного контента своим классам, отслеживание выполнения и разбор затруднений.

Дополнительная роль **Platform Admin** управляет заявками организаций, контентом, общими настройками и операционными процессами. Это не обычный школьный администратор.

### 1.2. Что НЕ делаем заново

- Не меняем React 19 + Vite на Next.js.
- Не пересоздаём лендинг, основные экраны, палитру, логотип, навигацию и Focus Mode без отдельной причины.
- Не генерируем второй ученический интерфейс для школ: школьник остаётся в Personal и получает раздел «Задания от школы».
- Не заменяем существующую структуру «урок → практика → тест → результат» абстрактным AI-чатом.
- Не проводим крупный визуальный редизайн в ходе создания backend.

**Допустимые изменения фронтенда:** исправление поведения, точечная адаптация форм, API-интеграция, реальные состояния загрузки и ошибок, улучшение навигации, доступности и адаптивности.

| Возможность | MVP (обязательно) | V1 после пилота | Позже |

## 2. Зафиксированное исходное состояние проекта

По результатам анализа предоставленного React-проекта:

- `src/App.tsx`: состояние авторизации, навигация, Focus Mode, активная школа, данные ученика и часть школьной логики.
- `src/services/schoolService.ts`: браузерное хранилище организаций, заявок, классов, членов, кодов, приглашений, заданий и результатов; при запуске добавляет демонстрационные данные.
- `src/components/auth/*`: UI регистрации, входа, подтверждения почты и восстановления пароля без завершённого серверного контура.
- `src/components/onboarding/OnboardingFlow.tsx`: настройка профиля ученика на клиенте.
- `src/components/dashboard/*`: личный кабинет и обзоры.
- `src/components/focus/*`: полноэкранные уроки, практика, пробный экзамен, результаты и повторение ошибок.
- `src/components/school/*`, `src/components/teacher/*`, `src/components/admin/*`: интерфейсы ролей.
- `src/content/*`: локальный демонстрационный контент и тестовые данные.
- `src/types/*`: предварительные TypeScript-типы.
- `package.json`: скрипты `dev`, `build`, `lint`; `lint` вызывает `tsc --noEmit`; исходные файлы `*.test.ts` есть, но единый тестовый runner в пакетных скриптах не организован.

**Известные риски, требующие исправления:**
1. Неавторизованный переход в `/school`, `/teacher`, `/admin/*` не защищён серверными правами; присутствует демонстрационный переключатель пространств.
2. `?autostart=1` открывает ученическую часть без корректной серверной идентификации: убрать из рабочей сборки.
3. `qazmind_auth_user` и другие общие ключи `localStorage` не являются надёжной авторизацией и смешивают данные разных пользователей браузера.
4. Логин/подтверждение email и приглашения не выполняют настоящие серверные операции.
5. Жёсткие `school_lyceum28`, `usr_teacher_daulet`, демонстрационная привязка ученика к лицею и фальшивые показатели должны остаться только в изолированном dev-seed.
6. При отсутствии нужных уроков/вопросов нельзя автоматически показывать чужую тему или чужой предмет.
7. В пробниках запрещено выдавать оценку «из 140» на основе 5 демонстрационных вопросов.
8. Школьные метрики нельзя считать из вымышленных fallback-значений.
9. Некоторые обновления школьных данных завязаны на повторную установку прежнего React-state: заменить нормальным cache invalidation/refetch.
10. Текущая навигация хранится в `App.tsx`; нужна полноценная маршрутизация с защищёнными маршрутами и восстановлением URL.

**Ограничение миграции:** старые данные в браузере и dev-seeds нельзя молча переносить в боевую БД как реальные аккаунты, подтверждения или школьные результаты.

## 3. Стек и архитектура

### 3.1. Утверждённый стек

**Frontend:** React 19, TypeScript, Vite, текущие Tailwind CSS 4/CSS, Lucide React и Motion. Допускается добавить React Router, TanStack Query и небольшой API-клиент. Изменение компонентной библиотеки без необходимости запрещено.

**Backend:** Python 3.12+ (конкретную поддерживаемую версию зафиксировать в репозитории), FastAPI, Pydantic v2, SQLAlchemy 2.x, Alembic, PostgreSQL 16+, async-драйвер PostgreSQL при выбранном async-подходе.

**Авторизация:** Argon2id для хранения хешей паролей; серверная сессия или короткоживущий токен в HttpOnly Secure cookie плюс управляемое обновление. Не хранить авторизационные токены и пароли в `localStorage`.

**Инфраструктура:** Docker Compose для разработки/пилота, HTTPS reverse proxy (Nginx/Caddy), SMTP или транзакционная почта, структурированные логи. Redis подключить при появлении фоновых задач, rate limiting или распределённых сессий; он не обязателен на первом коммите.

**Хранение файлов:** S3-совместимое объектное хранилище для изображений, образовательных вложений, будущих медиа. Для MVP допустим локальный dev-адаптер, но не публичный непроверенный каталог с загружаемыми файлами.

### 3.2. Принцип системы

```text
Browser (React/Vite)
  ├── Public / Auth / Onboarding
  ├── Student Workspace / Focus Mode
  ├── Teacher Workspace
  └── School / Platform Admin
        │ HTTPS + JSON
        ▼
FastAPI /api/v1
  ├── Auth & Sessions
  ├── User Profiles & Onboarding
  ├── Organizations & Memberships
  ├── Classes & Invitations
  ├── Curriculum & Content
  ├── Practice / Exams / Scoring
  ├── Assignments & Submissions
  ├── Progress & Analytics
  └── Operations / Audit
        │
        ├── PostgreSQL (источник истины)
        ├── Email provider
        ├── Object Storage (при необходимости)
        └── Background jobs (позднее)
```

**На первом этапе монолитный FastAPI backend:** одно приложение, отдельные доменные модули. Микросервисы сейчас не нужны. Все образовательные операции используют общие сущности и правила оценивания.

### 3.4. Сервер как источник истины

- Права, членства, уроки, опубликованные вопросы, ответы, результаты, лицензии и учебный прогресс берутся с API.
- Клиент хранит только UI-состояние, временный ввод и безопасные настройки отображения.
- Мутации возвращают каноническую сущность и обновляют query cache.
- Данные отображаются по состояниям `loading / success / empty / error / forbidden`.
- У всех записей серверные UUID/ULID и UTC timestamps; время отображается в часовом поясе пользователя/школы.

## 4. Аккаунты, роли и безопасность доступа

### 4.1. Идентичность

Один `users.id` на человека. Профиль студента отделён от его роли в организации. Один пользователь может учиться самостоятельно и принадлежать школе. Приглашение существующего пользователя не создаёт дубликат.

**Роли:** `STUDENT`, `TEACHER`, `SCHOOL_ADMIN` как роли внутри организации; `PLATFORM_ADMIN` как отдельно назначаемая глобальная привилегия. Для управления учебными материалами выделить отдельно `CONTENT_EDITOR` / `CONTENT_REVIEWER` либо granular permissions. Не давать школьному администратору права редактировать глобальный банк вопросов.

### 4.2. Матрица доступа

| Операция | Студент | Учитель | Админ школы | Админ платформы |
|---|---:|---:|---:|---:|
| Личный профиль/прогресс | Только свой | Только свой, если есть | Только свой, если есть | Только в утверждённых админ-процессах |
| Школьное задание | Выполнять назначенное | Создавать своим классам | Просматривать/организовать в своей школе | Аудит по обоснованному доступу |
| Классы | Свои | Назначенные | Все своей школы | По разрешённой административной операции |
| Приглашения учеников | Запросить вступление | Свои классы | Своя организация | Управлять организациями |
| Учителя и роли | Нет | Нет | Своя организация | Глобальные операции |
| Аналитика заданий | Свой результат | Свои классы | Агрегаты своей школы | По отдельному разрешению |
| Одобрение школы | Нет | Нет | Нет | Да |
| Публикация глобальных вопросов | Нет | Нет | Нет | Только уполномоченный редактор/ревьюер |

**Обязательно:** проверка роли, активного членства, `organization_id`, связи учителя с классом и принадлежности запрашиваемой сущности выполняется на сервере при КАЖДОМ запросе. Сокрытие пункта меню не заменяет проверки прав.

### 4.3. Авторизация и сессии

- Регистрация: имя, email, пароль; подтверждение email реальным одноразовым ограниченным по времени токеном.
- Проверка формата email, нормализация регистра, уникальность email, надёжное хеширование пароля.
- Вход по email/паролю; общие сообщения об ошибке учётных данных без перечисления пользователей.
- Password reset: одноразовый токен с истечением срока; не использовать предсказуемые ссылки.
- Сессии: ротация/отзыв, выход из аккаунта, ограничение числа неуспешных попыток, защита от CSRF для cookie-based auth, Secure/HttpOnly/SameSite и корректная CORS-конфигурация.
- После перезапуска браузера пользователь восстанавливается через `/auth/me`, а не через `qazmind_auth_user`.
- Для администрации и сотрудников предусмотреть MFA как требование перед реальным школьным пилотом либо при повышении риска; журналировать входы и изменения ролей.
- Админ платформы назначается только доверенной серверной операцией, не формой регистрации.

### 4.4. Маршруты

Public: `/`, `/schools`, `/schools/apply`, `/login`, `/register`, `/verify-email`, `/forgot-password`, `/reset-password`.  
Student: `/onboarding`, `/app`, `/app/subjects`, `/app/practice`, `/app/mock-exam`, `/app/progress`, `/app/mistakes`, `/app/settings`.  
Focus: `/learn/:subjectId/:lessonId`, `/practice/session/:sessionId`, `/exam/session/:attemptId`, `/exam/results/:attemptId`, `/review/:questionId`.  
School: `/school`, `/school/classes`, `/school/classes/:id`, `/school/teachers`, `/school/assignments`, `/school/analytics`, `/school/access`.  
Teacher: `/teacher`, `/teacher/classes/:id`, `/teacher/assignments`, `/teacher/assignments/:id/results`.  
Platform: `/admin/schools`, `/admin/schools/:id`; позже `/admin/content`.

Использовать router с nested layouts и guards. Проверять прямое открытие URL, browser Back и refresh. Focus Mode без сайдбара и нижней обычной навигации.

## 5. Ученики и онбординг

### 5.1. Путь нового ученика

`Лендинг → регистрация email → подтверждение → язык интерфейса/экзамена → 2 допустимых профильных предмета → цель до 140 → время подготовки → пустой персональный кабинет`.

Обязательные предметы добавляются программой автоматически. Комбинации профильных предметов хранятся в справочнике и привязаны к версии экзамена, а не только в TypeScript-массиве. Изменения правил можно публиковать без нового фронтенд-релиза.

Цель `140` является **желательным баллом**, а не достигнутым результатом. Выбранные предметы и цель можно менять в настройках без потери завершённых попыток.

Новый пользователь не наследует демонстрационные уроки, оценки, школу или ошибки. Для него показывается честное состояние «Начни первый урок» / «Пройди диагностику».

### 5.2. Персональный учебный кабинет

- Продолжить последний незавершённый урок.
- Показать 1–3 разумных следующих учебных действия.
- Показать назначенные школьные задания, если есть членство в школе.
- Дать доступ к предметам, Focus Lesson, Focus Practice, Focus Exam, ошибкам и личному прогрессу.
- Любая статистика должна происходить из завершённых/сохранённых операций.

### 5.3. Учебный прогресс

- `not_started`, `in_progress`, `completed` для урока; `completed_at` при достижении требований, а не при открытии страницы.
- Отдельная запись текущего шага или позиции для продолжения чтения.
- Повторение ошибок не означает освоение темы без последующей успешной проверки.
- Личный прогресс и контекст школьного задания могут обновляться одним событием завершения учебной активности, но не должны дублировать попытку.
- Настройки RU/KZ не изменяют результаты.

## 6. Школы и преподаватели

### 6.1. Заявка школы

`/schools/apply`: представитель создаёт или использует свой аккаунт, вводит название, тип учреждения, город, контактные данные и приблизительное число учеников. Заявка сохраняется как `pending`, подтверждение идёт через реальный email/интерфейс. Администратор QazMind может `approve/reject` с указанием причины; все действия аудируются.

Одобрение создаёт организацию и назначает проверенного представителя администратором школы. Запрещено самостоятельно нажатием ссылки или подменой статуса активировать школу.

### 6.2. Организация и классы

- Организация: `active`, `suspended`, `archived` (заявка отдельно `pending/approved/rejected`).
- Классы уникальны в пределах школы и учебного года по нормализованному названию (политику дублей настроить).
- У класса могут быть несколько учителей и много учеников.
- Учитель получает доступ только к явно назначенным классам и предметам, если используется предметная привязка.
- Учёт принадлежности к школе и членства в классе вести отдельными таблицами, не массивами ID в строке организации.
- Операции создания/смены класса не обнуляют личный прогресс ученика.

### 6.3. Приглашения и код класса

- Email-приглашения: случайный криптографически стойкий токен; хранить в БД хеш токена; ограничение времени и числа использований, возможность revoke и повторной отправки; учёт статуса.
- По коду класса: случайный уникальный код, срок действия, лимит использований, отложенное `join_request` с одобрением учителя/администратора (для пилота это выбранная политика по умолчанию).
- Существующий пользователь должен принять приглашение в своей учётной записи. Новый сначала регистрируется/подтверждает email.
- Учёт лимита мест и конкурентных операций транзакционный: одновременные заявки не создают сверхлимитных назначений лицензии.
- Отозванное/просроченное приглашение не работает даже по сохранённой ссылке.

### 6.4. Рабочее пространство учителя

Учитель видит **только назначенные классы**. Может:
- просматривать свои классы и учащихся, имеющих необходимый статус членства;
- создавать черновик задания и выбирать предмет, тему, урок, тест или валидный пробник;
- назначать своим классам, задавать дедлайн, лимит попыток и режим публикации результатов;
- видеть выполнение и проверенные ответы по школьным заданиям;
- закрывать/архивировать задание, не меняя прошлые попытки задним числом.

Учителю запрещено создавать задание по предмету без доступного проверенного контента; нельзя подставлять вопросы другой темы.

### 6.5. Жизненный цикл задания

`draft → published → closed → archived`.

Для ученика: `not_started → in_progress → submitted → evaluated`, с корректными событиями при истечении лимита или отмене. У каждой попытки свой ID, номер, снимок версии задания/состава вопросов и серверное время.

Попытки не должны перезаписывать друг друга. Политика итогового результата (например, лучшая попытка или последняя) фиксируется в настройках задания и показывается учителю явно.

### 6.6. Связка учебного задания с общим движком

- Школьное задание запускает тот же Focus Lesson / Practice / Exam, что и самостоятельное обучение.
- Попытка содержит `assignment_id` и `student_id`, а не создаёт параллельный, иной механизм проверки.
- После submit: сервер в одной транзакции сохраняет попытку, начисляет баллы, обновляет назначение и ставит пересчёт агрегатов.
- Итоги доступны студенту и соответствующему учителю согласно настройкам публикации.
- Школьные результаты доступны только адресатам с подтверждёнными правами.

### 6.7. Учёт лицензий

Для MVP: план, число мест, число занятых мест, срок, статусы. **Платёжный сервис не подключаем до отдельного задания.** При завершении лицензии платные права организации прекращаются по правилам подписки, но личная учётная запись ученика и принадлежащий ему прогресс не удаляются автоматически.

## 7. Система учебного контента

### 7.1. Справочники

В БД: экзаменационная версия, профильные пары, предмет, раздел, тема, урок, тип задания, принадлежность программы, язык/локализация, источники и статус публикации.

У урока: `id`, subject/topic, slug, title_ru/title_kz, body_ru/body_kz (безопасный структурированный формат), estimated_minutes, order, visibility, version, status, author/reviewer, published_at.

У вопроса: `id`, subject/topic, exam_version, question_type, stem_ru/stem_kz, content/assets, options/answer schema, explanation_ru/explanation_kz, difficulty, source_reference, review_status, version, publication status.

### 7.2. Типы вопросов

Обязательно проектировать расширяемый реестр типов:
- одиночный выбор;
- множественный выбор;
- соответствие;
- контекстный блок с зависимыми заданиями;
- при необходимости другие официально применимые виды.

Для каждого типа: frontend-renderer, DTO, схема валидации ответа, серверная функция scoring, тесты граничных случаев, корректное отображение разбора.

**Никогда:** не отправлять правильные ответы и закрытые схемы начисления баллов в payload активного экзамена до завершения/разрешённой публикации результатов. Сохранённые ответы студента проверяются на сервере.

### 7.3. Публикация и качество

Этапы материала: `draft → in_review → approved → published → archived`.

До публикации: полнота RU/KZ по заявленным языкам, проверенная правильность, однозначная формулировка, отсутствие дубликатов/ошибок, указание автора/источника и прав использования. Контент, извлечённый из чужих платных банков вопросов без разрешения, в продакшен не импортировать.

Минимальный CMS: перечень, создание/редактирование, проверка, публикация, архив, массовый импорт только через валидацию. Для самого первого пилота допускается CLI/importer для проверенных материалов и простой интерфейс управления вместо богатого редактора.

### 7.4. Версионирование

Результат попытки привязан к `content_version` и `exam_spec_version`. Исправление опубликованного вопроса создаёт новую версию или сохраняет неизменяемый snapshot для прежних попыток. Нельзя пересчитывать исторические результаты по новым ответам без отдельного аудируемого процесса исправления.

## 8. Подготовка к ЕНТ и экзаменационный движок

### 8.1. Базовые параметры

На дату ТЗ Национальный центр тестирования публикует для основного общего формата ЕНТ на нетворческие специальности: **5 предметов, 120 заданий, максимум 140 баллов, 240 минут**. Обязательные: история Казахстана — 20 заданий, грамотность чтения — 10, математическая грамотность — 10; профильные — по 40 заданий, по 50 баллов. Часть профильных заданий оценивается более чем в один балл. [НЦТ: формат](https://new.testcenter.kz/?lang=ru&page_id=15074), [информация для абитуриентов-2027](https://testcenter.kz/?custom_news_section=%F0%9F%8E%93%D1%83%D0%B2%D0%B0%D0%B6%D0%B0%D0%B5%D0%BC%D1%8B%D0%B5-%D0%B0%D0%B1%D0%B8%D1%82%D1%83%D1%80%D0%B8%D0%B5%D0%BD%D1%82%D1%8B-2027&lang=ru).

**Нельзя зашивать эти цифры в компоненты:** хранить версию формата, список предметов, количество и типы вопросов, ограничения и функцию оценивания как проверяемую спецификацию. При появлении новых официальных правил выпускать новую версию спецификации, старые попытки не менять.

Иные категории ЕНТ (творческие, сокращённая форма и др.) не смешивать с основным форматом; до отдельного проектирования считать вне MVP.

### 8.2. Практика vs пробный экзамен

| Режим | Источник заданий | Результат |
|---|---|---|
| Практика | Набор опубликованных вопросов нужного предмета/темы | Число правильных и детализация |
| Тематический тест | Проверенный набор с настройками | Баллы по установленной схеме этого теста |
| Демо на 5 вопросов | Явно помеченный демонстрационный комплект | Только фактический итог, например 4/5 |
| Полноценный пробник | Комплект по конкретной `exam_spec_version` | Корректный балл по правилам версии; максимум 140 для соответствующей версии |

Если нужного контента недостаточно, кнопка полного пробника не запускает фиктивный вариант. Показывать «Пробный экзамен пока недоступен» либо безопасный демо-режим с точным обозначением.

### 8.3. Сессия экзамена

- Создание попытки на сервере с `started_at`, `expires_at`, `exam_form_id`, `status`.
- Сервер фиксирует состав и последовательность заданий; API выдаёт вопросы без эталонных ответов.
- Автосохранение ответов с idempotency и контролем допустимого состояния сессии.
- Таймер рассчитывается из серверных дат; клиентское время только визуализация, обновление вкладки не продлевает тест.
- Состояния `created`, `in_progress`, `submitted`, `expired`, `evaluated`, `cancelled`.
- Повторная отправка submit не создаёт второй результат.
- Время истекло → зафиксировать завершение и проверить принятые ответы в соответствии с правилами.
- Результат: баллы по предметам и типам заданий, ошибочные/неотвеченные, разрешённый разбор; не показывать индивидуальный или прогнозируемый «официальный балл», если тип варианта не соответствует полному формату.
- Предусмотреть согласованное поведение при временной потере сети: индикатор сохранения, локальная очередь непринятых вводов без записи секретов, явное предупреждение, retry и проверка версии.

### 8.4. Доступность

Для отдельных категорий участников официальный режим может предусматривать дополнительные условия времени. Модель спецификаций должна поддерживать индивидуально назначаемое дополнительное время и исключения без ручного обхода клиента; актуальные правила подтверждать перед реализацией.

## 9. Персональный маршрут и аналитика

### 9.1. Правила первой версии

Персональный маршрут MVP — **детерминированный**, без обязательного AI: выбранные предметы + доступные темы + тестовые результаты + дата экзамена (если известна) + дневная цель. Приоритет: незавершённый урок, запланированное задание школы, недавно допущенные ошибки, следующая тема учебной программы.

«Освоение темы» нельзя считать только от прочитанных страниц: вводится прозрачная шкала, например статус темы на основе выполнения уроков и минимальной выборки тренировочных ответов. Алгоритм записать в документации, при недостатке данных отображать «Мало данных», а не `83% освоено`.

### 9.2. Ошибки и повторение

`mistake_items`: студент, question_id/version, attempt_id, тип ошибки, последнее появление, состояние повторения. История ошибок хранится; при успешном повторении состояние обновляется, но факт прошлой ошибки не исчезает из статистики. Разрешать повторение только тех вопросов, которые студенту доступны по текущим правам.

### 9.3. Школьная аналитика

Только реальные данные и только подтверждённые школьные задания. Метрики: выполнение, средние результаты **по сопоставимым тестам**, распределение ошибок по темам, количество не начавших/завершивших. Раздельно показывать числитель и знаменатель (например, 18 из 25). Не строить «прогноз 140» из пяти вопросов.

Личные AI-разговоры, частные заметки и самостоятельная учебная история не должны автоматически раскрываться школе.

| GET | `/organizations/{orgId}/analytics` | Школьные агрегаты |
| GET | `/organizations/{orgId}/licenses` | Учёт мест и срока |
| GET | `/admin/school-applications` | Очередь модерации |
| POST | `/admin/school-applications/{id}/approve` | Одобрить |
| POST | `/admin/school-applications/{id}/reject` | Отклонить |

**Никаких клиентских `studentId`, `teacherId` или `orgId` в роли доказательства прав.** Server user ID берётся из сессии. Все операции с `orgId` проходят проверку членства/полномочий.

### 11.4. Примеры контрактов

```json
POST /api/v1/me/onboarding/complete
{
  "interface_lang": "ru",
  "exam_lang": "ru",
  "profile_pair_id": "math_phys",
  "target_score": 140,
  "exam_year": 2027,
  "daily_goal_minutes": 30
}
```

```json
POST /api/v1/organizations/{orgId}/assignments
{
  "title": "Казахское ханство: практика",
```

Это **примеры**, не готовые схемы БД: реальные UUID и поля контракта формализовать в Pydantic/OpenAPI после создания моделей.

### 11.5. Ошибки API

Минимум: `400` неверный формат, `401` неавторизован, `403` нет разрешения, `404` ресурс не виден/не существует, `409` конфликт/дубликат/ограничение мест, `422` ошибка валидации, `429` превышение лимита, `5xx` ошибка сервера. Не раскрывать чужую организацию через различие текстов 403/404, когда это создаёт информационную утечку.

```json
{
  "error": {
    "code": "NO_AVAILABLE_QUESTIONS",
    "message": "Для этой темы пока нет опубликованных заданий",
    "request_id": "trace-id"
  }
}
```

## 12. Интеграция существующего фронтенда с API

### 12.1. Без изменения дизайна

Этапы:
1. Зафиксировать текущий внешний вид скриншотами (desktop/mobile) и успешной сборкой.
2. Выделить `apiClient`, DTO, `AuthProvider`, `QueryClient`/аналог для загрузки и кэша.
3. Убрать `currentUser`/авторизационные fake-схемы из `App.tsx`; профиль получать `/auth/me` и `/me/profile`.
4. Перенести данные школ из `schoolService.ts` в API adapter. Старый сервис оставить исключительно в dev-demo режиме или удалить после завершения миграции.
5. Перевести классы, задания, приглашения и результаты на REST-запросы.
6. Перевести учебный прогресс и попытки на сервер, сохранив Focus-компоненты.
7. Удалить обходной `autostart=1`, фиктивный `WorkspaceSwitcher` и жёстко заданного учителя.
8. Показать загрузку, отсутствие данных и честную ошибку сети в существующем стиле.
9. Перевести навигацию на защищённые вложенные маршруты.

### 12.2. Где оставить локальное состояние

Допустимо: открытые вкладки, свёрнутый сайдбар, незаполненная форма, открытый модал, локаль до входа. Не допускается как источник истины: роли, авторизация, школьные членства, оплаченные места, результаты экзаменов, эталонные ответы, глобальный учебный прогресс.

### 12.3. Демо-режим

При необходимости создать явный `DEMO_MODE` только для локальной разработки или отдельного публичного демонстрационного окружения: изолированные тестовые организации и ученики; надпись «Демонстрация», запрет реальных персональных данных, никакого смешивания с production.

## 13. AI-помощник — отдельная версия, не блокер MVP

Цель: подсказки по текущему уроку, объяснение ошибки, примеры похожего уровня. **Не** автоматическая проверка официальных ответов и не необязательный для обучения чат.

Сервис запускается только на backend: API-ключи не попадают в клиент. Вход: разрешённый урок/вопрос, тип запроса, язык, достаточный проверенный контекст. Выход: короткое объяснение с проверкой формата/ограничениями; при отсутствии контекста — отказ от уверенного ответа и ссылка на материал. Не раскрывать правильный ответ до допустимого этапа теста.

Не передавать третьему AI-провайдеру избыточные личные данные ученика или школьные идентификаторы. Ввести квоты и стоимости запросов, мониторинг качества и модерацию. Этап возможен после стабильных уроков, практики, результатов и согласований по данным.

## 14. Администрирование платформы и контента

**Platform Admin:** очередь школьных заявок, управление статусом организаций, расследование ошибок, аудит административных действий и технические метрики. Никакого неограниченного просмотра ученических данных без подтверждённой цели и регламента.

**Content Editor/Reviewer:** создание, проверка, публикация уроков и заданий, журнал версий, импорт по формату и отчёт об ошибочных вопросах. Редактор не может самоутверждать контент, если предусмотрена двухэтапная проверка. Экспорт учебных материалов ограничен их лицензией.

**Поддержка:** сообщения/тикеты (можно в V1), идентификатор запроса для расследования, механизм сообщения об ошибке в вопросе.

## 15. Нефункциональные требования

### 15.1. Производительность (целевые показатели для пилота)

- Поддержка не менее **300 одновременно активных пользователей** в пилотном окружении после нагрузочного теста, без обещания мощности до тестирования.
- Цель `p95 <= 500 мс` для типовых GET API без тяжёлых отчётов при согласованном пилотном профиле нагрузки; отдельно измерить write/autosave.
- Автосохранение ответа при нормальном соединении без явной потери; retry безопасен.
- UI корректно работает на мобильных экранах от 390 px и основных поддерживаемых браузерах.
- Медленные отчёты и рассылки не блокируют основные экзаменационные операции.

### 15.2. Надёжность

- Транзакционная запись критичных операций (назначение места, принятие приглашения, submit, оценивание).
- Idempotency для submit экзамена, принятия приглашения и массовых действий.
- Бэкапы PostgreSQL ежедневно, проверяемое восстановление не реже одного раза за пилотный период, отдельно хранить резервные ключи/конфигурации.
- Мониторинг API ошибок, очередей, писем, сбоев экзамена и заполнения диска.
- Все сервера и БД в UTC; фронтенд показывает локальное время; дедлайны хранятся offset-aware.

### 15.3. Безопасность/приватность

- HTTPS, HSTS после проверки, rate limiting, проверки входных данных, защита CSRF/XSS/SQLi, ограничения загрузок, отсутствие секретов в Git.
- RBAC + проверки изоляции школ и привязки к классу на уровне сервиса/запроса. Если применяется PostgreSQL RLS, оно усиливает, а не заменяет корректные запросы.
- Аудит массовых приглашений, изменения полномочий, экспорта и просмотра чувствительных записей по утверждённым сценариям.
- Минимизация собираемых данных; политика хранения и удаления, запросы на доступ/исправление, проверка законных оснований обработки и согласий с учётом несовершеннолетних и локальных требований РК.
- Перед запуском с реальными школьниками нужна юридическая проверка документов, договоров со школами, законных оснований обработки, фактического места хранения персональных данных и правил доступа; требования Казахстана могут зависеть от модели оператора и обработки.

Справочно: [Закон о защите персональных данных и позиция госоргана](https://www.gov.kz/org/infsecurity/press/press-releases/details/16593?lang=ru), [права граждан](https://www.gov.kz/situations/421/intro?lang=ru), [рекомендации по безопасности](https://www.gov.kz/org/maidd/press/news/details/1277592).

### 15.4. Локализация и доступность

- Все ключевые действия RU/KZ; интерфейс различает язык приложения и экзамена.
- Контент не переключается без предупреждения на другой язык при отсутствии перевода.
- Поддержка клавиатуры, видимого focus, подписей формы, корректного контраста, не полагаться только на цвет.
- Полноэкранный Focus Mode браузера не требует fullscreen permission; это отдельный layout без сайдбара.

**C. Ученик в школе**: самостоятельно зарегистрированный студент принимает приглашение в класс → личный прогресс не исчезает → видит школьное задание → Focus Mode → сдаёт → учитель видит реальный результат.

**F. Нет данных**: если отсутствуют опубликованные вопросы, приложение не выбирает случайный чужой предмет и не рисует фальшивую оценку.

## 17. DevOps и окружения

### Окружения

- `local`: локальный Docker Compose с PostgreSQL, backend и frontend; тестовая почта Mailpit или эквивалент, без реальной рассылки.
- `staging`: отдельные БД, ключи и тестовые организации; воспроизведение production процессов.
- `production`: отдельные секреты, данные, резервные копии, HTTPS и мониторинг.

### CI

Pull request должен запускать frontend typecheck/build/tests, backend lint/typecheck/tests, проверку миграций, минимальные security checks. Merge в основную ветку через PR; rollback через версионированные Docker images и безопасную схему миграций.

### `.env.example`

Только наименования переменных и безопасные заполнители: `DATABASE_URL`, `APP_ENV`, `PUBLIC_APP_URL`, `API_CORS_ORIGINS`, `SESSION_SECRET`/ключи, `MAIL_*`, `STORAGE_*`. Не копировать секреты AI Studio в публичную сборку. Для фронтенда только публичный `VITE_API_BASE_URL` или reverse proxy `/api`.

### Запуск одним README

Документировать:
1. требования к среде;
2. `docker compose up -d`;
3. команды миграций;
4. создание dev-admin только через безопасную CLI-команду;
5. запуск backend и Vite;
6. seed демонстрационных данных, отдельно и явно;
7. тесты;
8. резервное копирование и восстановление.

## 18. Поэтапный план реализации (backlog для Claude Code)

Задачи выполняются последовательно. **Каждый этап должен завершаться работоспособной сборкой и коммитом.** Указанные сроки не утверждаются, оценивать после первичного запуска и ревизии проекта.

### Этап 0 — технический аудит и baseline [P0]

- Развернуть исходный проект, зафиксировать текущие экраны/URL и сценарии.
- Добавить README со структурой и диагностикой проблем, создать новую ветку.
- Зафиксировать зависимые версии; `npm ci`/`npm install`, `npm run build`, `npm run lint`.
- Добавить тестовый runner для текущих TS-tests.
- Сохранить screenshots главных экранов для регрессионной проверки.

**Готово, когда:** проект запускается локально, есть baseline и список рисков, внешний вид не изменён.

### Этап 1 — backend skeleton + PostgreSQL [P0]

- FastAPI, конфигурация, Health endpoints, async/sync strategy, DB connection, Docker Compose.
- SQLAlchemy, Alembic initial migration, общая модель ошибок и request IDs.
- Автотесты БД и API, базовый CI.

**Готово, когда:** сервер поднимается чистой командой, схема БД создаётся миграциями, health/readiness проходят.

### Этап 2 — аккаунты и сессии [P0]

- Реальные регистрация/email verification/login/logout/reset.
- Сессии HttpOnly-cookie, CSRF, лимитирование, `/auth/me`.

- Удалить production-доступ через `?autostart=1` и demo-permission switching.

**Готово, когда:** чужой пользователь не может открыть кабинет/админку; неверный пароль отклоняется, повторный вход и выход работают.

### Этап 3 — онбординг и личный профиль [P0]

- Профиль/пары предметов/цель/языки/дневная норма в БД.

**Готово, когда:** два человека на одном браузере видят разный собственный прогресс, данные доступны после входа с другого устройства.

**Готово, когда:** валидный состав варианта автоматически проверяется; все баллы по официально утверждённой версии начисляются правильно.

### Этап 10 — аналитика/качество/пилот [P1]

- Метрические endpoints, real-data прогресс и отчёты, минимальная контент-админка.

- Юридические/организационные проверки для школьников и пилот на ограниченной группе.

**Готово, когда:** все негативные тесты прав пройдены, данные резервируются, нет видимых демонстрационных фикций и есть протокол пилота.

Контекстный AI-репетитор, расширенная адаптивная учебная программа, автоматическое выставление счетов и подписок, экспорт отчётов, родительский кабинет, интеграции со школьными системами, мобильное приложение, глубокая аналитика и дополнительные форматы экзаменов. ## 19. Приоритеты для одного разработчика

**Немедленно:** этапы 0–3: локальный запуск, backend, auth, onboarding. Без этого ничего нельзя безопасно подключать к реальным школам.

**Затем:** этапы 4–5: хотя бы один предмет с действительно качественным контентом, уроком, практикой, проверкой и сохранением результата. Не расширять каталог предметов ради количества.

**После этого:** этапы 6–8: один реальный школьный процесс от приглашения до результата. Это и есть подтверждение полезности B2B-версии.

**Только потом:** полноценные пробники и сложная аналитика. AI-подсказки, платежи и мобильное приложение не должны задерживать базовый релиз.

### Правило разработки с Claude Code

Каждую задачу давать как отдельный небольшой тикет со следующими полями:

```text
ID: QM-XXX
Цель:
Контекст текущих файлов:
Что изменить:
Что НЕ менять:
Данные/API-контракт:
Граничные случаи и права:
Тесты:
Команды проверки:
Критерии готовности:
```

**Не давать команду «реализуй весь QazMind» за один заход.** Перед большим изменением Claude должен перечислить затрагиваемые файлы и риски, затем выполнить одну фазу с тестами.

## 20. Definition of Done — единые правила приёмки

Задача считается завершённой, когда:

1. Исходная задача и затронутые файлы описаны в PR/коммите.
2. Код не содержит секретов или демонстрационных обходов авторизации.
3. Контракты данных типизированы; backend валидирует входные параметры.
4. RBAC/tenant checks покрыты негативными тестами там, где задействованы роли/организации.
5. Миграция БД создана, применяется с чистой БД и имеет понятную обратимость либо безопасный migration plan.
6. UI сохраняет фирменный вид и корректно обрабатывает loading/empty/error.
7. `npm run lint`, `npm run build`, frontend tests, backend tests проходят.
8. При необходимости пройден E2E-сценарий в staging.
9. README/API docs обновлены.
10. Функция проверена после refresh и повторного входа под разными аккаунтами.

## 21. Бизнес- и продуктовые критерии первого пилота

Не выдавать целевые показатели за достигнутые. Предложение для измерения:

- Доля завершивших регистрацию и онбординг.
- Доля учеников, завершивших первый урок.
- Доля начавших практику после урока.
- Доля заданий школы, выполненных к сроку.
- Количество попыток с потерянными данными (цель: 0 подтверждённых случаев).
- Количество ошибок доступа между школами (цель: 0).
- Скорость прохождения сценария «админ создал класс → учитель назначил → ученик сдал → учитель увидел результат».
- Оценка удобства и замечания реальных участников пилота.

Начальный пилот: 1 образовательная организация, ограниченный круг пользователей и только при выполнении требований безопасности, согласий/разрешений, доступов и хранения данных.

## 22. Открытые решения до реализации соответствующих модулей

1. Хостинг и фактическое размещение данных с учётом требований Казахстана (обязательно проверить до реальных аккаунтов/школ).
2. Почтовый провайдер и доменная почта `qazmind.asia`.
3. Модель сессии: серверный session store vs cookie tokens; зафиксировать ADR, выбранная реализация обязана поддерживать отзыв/ротацию и CSRF.
4. Публичная политика обработки данных несовершеннолетних, порядок согласий законных представителей и договор со школой.
5. Политика нескольких школ для одного ученика и конкурирующих школьных лицензий.
6. Политика преподавательских прав по предметам и классам.
7. Правило итоговой оценки задания с несколькими попытками.
8. Уровень контентного покрытия MVP и кто экспертно проверяет задания.
9. Какие официальные форматы ЕНТ поддерживаем в первом релизе; все остальные пометить недоступными.
10. Ценовая модель школы/подписки; до утверждения не внедрять фиктивные платежи.

Эти решения не блокируют **этапы 0–1**, но должны быть приняты перед реализацией затрагиваемого функционала.

## 24. Что считать завершением проекта первой версии

**QazMind MVP принят**, если существует работающее staging/production-like окружение, где:

1. Новый ученик регистрируется и подтверждает реальную почту.
2. Он задаёт профильную пару и целевые 140 баллов, видит свой пустой кабинет.
3. Он проходит проверенный урок и практику, сохраняет результат; другой браузер показывает тот же прогресс.
4. Представитель школы подаёт заявку, которую может одобрить только платформенный администратор.
5. В школе создаются класс и настоящий учитель через приглашение.
6. Учитель назначает доступный тест; ученик видит и проходит его через fullscreen Focus Mode.
7. В PostgreSQL сохраняются попытка, ответы, корректный балл, привязка к школьному заданию и школьной аналитике.
8. Учитель видит завершение **только своих** учеников; другой класс/школа изолированы.
9. Отсутствующий контент и пустая статистика не подменяются фальшивыми данными.
10. Систему можно развернуть из Git репозитория по README, миграциям и `.env.example`, есть тесты и резервное копирование.

**Конец ТЗ 1.0.** Новые продуктовые идеи добавлять через backlog и отдельные ADR/ТЗ, не расширяя бесконтрольно MVP.
